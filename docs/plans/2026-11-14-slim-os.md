# Plan: Hector9000 auf ein schlankes OS umziehen

Stand 2026-11-14. Status: **Plan, nicht umgesetzt.**

## Warum

Ist-Zustand (aus der SD-Karte gelesen): Raspberry Pi OS **Bullseye Desktop**
(pi-gen stage4, Image vom 2023-05-03), volle LXDE-Oberfläche, Chromium-Kiosk
darüber, Backend per `start.sh` mit `nohup`.

- **Bullseye ist EOL:** keine Sicherheitsupdates mehr, die Debian-Paketquellen
  liegen nur noch auf `archive.debian.org` (im Test ist `apt` an den alten Quellen
  gescheitert). Jede Nachinstallation wird mühsam.
- **Viel Ballast:** Desktop, Dateimanager, Panel, Hintergrunddienste. Das kostet
  Bootzeit, RAM und SD-Karten-Schreibzugriffe und vergrößert die Angriffsfläche.
  Hector braucht davon nur Chromium im Vollbild.
- **Fragiler Start:** `start.sh` mit `nohup` startet nichts neu, wenn ein Dienst abstürzt.

Ziel: **Raspberry Pi OS Lite (aktuelle Version, 64-bit)** ohne Desktop, darauf nur
mosquitto, die drei Hector-Dienste und ein Kiosk-Compositor mit Chromium, alles als
systemd-Dienste. Erwartung: Boot bis zur UI deutlich unter 30 s (heute grob eine
Minute, auf dem Pi zu messen), weniger RAM, wartbar per `apt`.

## Zielbild

| Baustein | Lösung |
|---|---|
| OS | Raspberry Pi OS Lite, 64-bit, aktuelle Version |
| Kiosk | `cage` (Wayland-Kiosk-Compositor: eine App, Vollbild, Touch) + Chromium als systemd-Dienst auf tty1 |
| Backend | systemd-Units `hector-server`, `hector-controller` (User `hector`), `hector-led` (root, wegen WS2812/PWM), `Restart=on-failure` |
| Python | eigenes venv mit aktualisierten Abhängigkeiten statt systemweitem `setup.py develop` |
| MQTT | mosquitto, 1883 nur `localhost`, Websocket 9001 (Bind-Adresse siehe offene Fragen) |
| Einrichtung | ein idempotentes Skript `deploy/provision.sh` im Repo; neu aufsetzen = Imager + Skript |
| Optional | Overlay-Dateisystem (Root schreibgeschützt) gegen SD-Schäden bei Stromausfall an der Bar |

**Vollbild verlassen** ändert seine Bedeutung: Ohne Desktop gibt es nichts „dahinter“.
Der geheime Exit stoppt dann den Kiosk-Dienst und es erscheint die Text-Konsole (oder
ein kleines Wartungsmenü, siehe offene Fragen). `HectorSystem` ruft dafür
`systemctl stop hector-kiosk` statt `pkill` auf; das Flag-/Lock-Verfahren von
`kiosk.sh` entfällt.

## Schritte

1. **Bestandsaufnahme vom laufenden Pi** (per SSH oder aus `update.log`):
   Pi-Modell, Netzwerk (WLAN/Ethernet), mosquitto-Konfiguration, lokale Änderungen
   in `HectorConfig.py` (Kalibrierung `hx711.ref`, Ventilpositionen), `drinks.py`,
   Datenbank `h9k.db`, sudo-Rechte, eventuell angepasste Startskripte.
2. **Sichern:** komplettes Image der aktuellen Karte (Fallback) und die Daten aus Schritt 1
   separat.
3. **Kompatibilitäts-Spike (größtes Risiko):** Die Hardware-Bibliotheken sind alt
   (`Adafruit-PCA9685` 1.0.1, `Adafruit-GPIO`, `RPi.GPIO` 0.7, HX711, `adafruit-circuitpython-neopixel` 6.0,
   Pins aus 2019) und laufen nicht zwingend auf aktuellem Python (3.13).
   Auf einer **zweiten SD-Karte** Lite installieren, venv bauen und mit `tools/hardwaretesttool.py`
   Waage, Ventile (PCA9685), Pumpe, Arm und LEDs prüfen. Bei Bedarf auf die gepflegten
   CircuitPython-Pakete umstellen (`adafruit-circuitpython-pca9685`, `-hx711`, `rpi_ws281x`).
   Erst wenn das läuft, weitermachen.
4. **`deploy/provision.sh` schreiben** (idempotent, als root):
   Pakete (`git mosquitto chromium cage python3-venv`), I²C an (`raspi-config nonint do_i2c 0`),
   User `hector` mit Gruppen `gpio i2c spi video render input`, mosquitto-Konfiguration,
   venv + Abhängigkeiten, systemd-Units, Kiosk-Dienst, optional Overlay-Dateisystem.
5. **Code-Anpassungen:** systemd-Units und Kiosk-Dienst ins Repo, `HectorSystem`-Exit auf
   `systemctl stop hector-kiosk`, `requirements.txt` aktualisieren, `start.sh`/`kiosk.sh`
   nur noch für Altinstallationen.
6. **Testlauf auf der zweiten Karte** mit echter Hardware: Boot-Zeit messen, Drink dosieren,
   Reinigen, LED-Modi, Reboot-Button, geheimer Exit, Stromausfall-Test (Stecker ziehen).
7. **Umstieg:** Daten (Kalibrierung, `h9k.db`) übernehmen, zweite Karte einsetzen, alte Karte
   als Fallback aufheben.

## Aufwand und Risiko

- Provisionierung und Kiosk: überschaubar (etwa ein Tag inkl. Test).
- Hardware-Bibliotheken auf neuem Python: **unbekannt**, deshalb der Spike in Schritt 3 vor allem anderen.
- Kein Risiko für die laufende Maschine, solange auf einer zweiten Karte gearbeitet wird.

   (der Pi 5 braucht andere).
2. Was soll nach dem geheimen „Vollbild verlassen“ zu sehen sein: Text-Konsole reicht,
   kleines Wartungsmenü (Neustart, IP anzeigen, Kiosk wieder starten), oder doch ein Mini-Desktop?
3. Soll die WebUI auch von anderen Geräten im Netz erreichbar sein? Wenn nein, bindet mosquitto
   nur an `localhost` (schließt nebenbei die offene Reboot-/Dosier-Lücke über MQTT).
4. Gibt es eine zweite SD-Karte für den Testaufbau?
5. Overlay-Dateisystem ja/nein? Schützt die Karte, aber Datenbank-Änderungen brauchen dann einen
   eigenen beschreibbaren Bereich.
